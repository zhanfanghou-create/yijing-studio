# 艺镜 Studio · 仙宫云部署方案（Qwen-Image-2.1 + Qwen3-TTS-1.7B + MiniMax H3）

> 目标机型：单卡单机，不装 ComfyUI。**装什么、装不装先看第零节** ——
> 24 GB 的卡四个模态全都能跑（视频走 NF4 + disk offload，慢一档），48 GB 上同一条片子快 2–3 倍。
> 权重一律放云盘，**镜像只留 9 G（上限 30 G）**，模型靠配置检测面板按需装。
> 交付形态：浏览器打开 `http://<平台地址>` 就是画布，四个模态全在机器上跑。
> 本文档对应 `deploy/` 下的文件，都是能直接执行的，不是示意。

---

## 零、镜像只放代码，模型按显存按需装

两条原则，顺序不能反。

**原则一：权重不进镜像。** 仙宫云按小时计费，镜像里塞几十 G 权重等于每次开机都在为它付钱。
所以系统盘只放代码 + Python 环境（实测压到 **9.0 G**，上限 30 G），
所有权重放云盘 `/root/cloud/models`（webdav，不计入镜像）。

**原则二：权重哪几份看这张卡的显存。** 全套装下来 94 GB，但 24 G 的卡装 Qwen-Image 要开
offload、装 H3 靠 disk offload，不是「装得越多越好」。`vram-plan.sh` 读单卡显存给结论：

```bash
bash deploy/vram-plan.sh          # 人看的清单，带理由
bash deploy/vram-plan.sh --json   # 给脚本消费
bash deploy/vram-plan.sh --want   # 只输出要装的 key，喂给 bootstrap
```

实测输出（RTX 4090 D / 24 GB —— 就是现在这台一体机）：

```
  显卡    NVIDIA GeForce RTX 4090 D
  显存    24 GB（单卡最大；按单卡判，不按多卡求和）
  档位    standard — 24 G 级 · 生图要 offload，视频走 NF4

  状态 模型                           磁盘 需显存  说明
  可跑 Qwen3-8B 对话                     16G      18G  bf16 权重；24 G 卡要限制上下文长度才留得下 KV cache
  勉强 Qwen-Image-2.1 生图               31G      24G  transformer 约 20 G + 文本编码器；必须开 offload
  可跑 MiniMax-H3 视频（唯一后端）        34G      12G  NF4 只收 FL2VA 四件；官方 README：最低 8 G 显存
  可跑 Qwen3-TTS-1.7B 三件套             13G       6G  同一时刻只驻留一个

  该装    text image video voice
  磁盘    约 94 GB（这套机器全能装）
```

四个要点：

1. **视频只有 MiniMax H3 一个后端。** Wan2.2 那一档已经从代码里删干净了
   （`deploy/video_worker.py` 入口收到非 H3 的模型名会直接抛错，不再静默换模型出片）。
2. **H3 只下 NF4 的 FL2VA 四件（34.4 GB），不下官方 bf16 全量（171 GB / 125 GB 显存）。**
   NF4 仓库里躺着 5 个大分片共 72.5 GB，其中 `ref2va-*` 和两个 `-pruned-` 是另一条管线和精简版，
   全收白占 38 GB。`bootstrap.sh models video` 已按文件白名单下，官方全量必须显式点名
   `models video-full` —— 连 `models all` 都不会带上它。
3. **判据是「单卡最大显存」，不是多卡求和。** 这套推理是按「一个管线放一张卡」写的，
   不会把 H3 的层切到两张卡上，所以 2×24 GB ≠ 能跑 48 GB 的模型。
4. **装完落在云盘，不落系统盘。** 配置检测面板上点「下载」也是这样：下载跑在宿主进程里
   （`web/host.mjs` 的 `DL_SPECS`），落盘根 `YJ_INSTALL_ROOT` 默认就是 `/root/cloud/models`，
   所以下次存镜像不会把它算进去。镜像瘦身和「功能可用」因此不冲突。

想换机器算账、或者写文档时不想真跑 GPU，可以给假值：

```bash
YJ_VRAM_MB=49140 YJ_GPU_NAME="RTX 6000 Ada" bash deploy/vram-plan.sh
```

## 一、先说结论：显存要够，而且得接受一条纪律

下面的数字是**24 GB 这一档**的排布（就是这台机器）。24 G 上视频走 NF4 + disk offload，
能出片但慢；48 GB 以上不需要 offload，同一条片子快 2–3 倍。

四个模态**不能永远同时驻留**。这不是实现问题，是物理问题：

| 模态 | 模型 | 权重 | 显存（常驻/峰值） |
|---|---|---|---|
| 文本 | Qwen3-8B-Instruct（transformers，限制上下文） | 16 GB bf16 | ~7–18 GB |
| 语音 | Qwen3-TTS-12Hz-**1.7B** 三件套（同一时刻只驻留一个） | 3.9 GB/个 + 0.68 GB codec | ~5–6 GB |
| 图片 | **Qwen-Image-2.1** 7B + Qwen3-VL-8B 编码器 | 33 GB bf16 | **~22 GB**（开 offload） |
| 视频 | **MiniMax H3-Base** 33B + Qwen3-VL-32B 编码器（NF4 量化） | **34.4 GB**（FL2VA 四件） | 最低 8 GB（disk offload），实用 12–24 GB |

所以编排只有三档，`model-server.py` 里用「租约」表达。**48 GB 档**是干净的情形：

```
空闲     语音 6 + 文本 7                     =  13 GB   ← 开机常态
出图     + 图片 22                           =  35 GB   ✅ 余 13 GB
出视频   语音必须让位 → 文本 7 + 视频 34     =  41 GB   ✅ 余 7 GB
```

**24 GB 档**（这台）挤得多，视频得靠 offload：

```
空闲     语音 6 + 文本 7                     =  13 GB
出图     图片 offload 压到 ~18 GB + 语音 6   =  24 GB   紧，出图慢一档
出视频   语音让位；DiT 只驻留一小部分，其余按需换入换出 → 能跑，慢
```

**唯一的纪律：生成视频时不能同时配音。** 提交视频任务前，`model-server` 会调语音引擎的
`POST /unload` 把 1.7B 权重还回去；任务结束（子进程退出，显存 100% 归还驱动）后，
下一次点合成时语音自己重载，冷启动 4–8 秒。24 G 档上还要更克制一点：出视频时别同时开
对话或批量出图，那几个 G 正是 DiT 需要的余量。

这个取舍是有依据的：你的实际工作流是「先出片，再配音」。让两个 30 GB 级的模型抢一张卡，
结果只会是两边都 OOM，而且报错点永远在另一个进程上，极难排查。

## 二、三个模型的真实情况（含许可，请先看第 7 节）

### 1. 图片：Qwen-Image-2.1（2026-09-20 开源）

比上一代 FLUX/SDXL 多出来的正好是画布需要的三件事：

- **原生 RGBA 透明**。VAE 是 64 通道带 alpha，提示词里写 `RGBA image with transparency`
  就直接出透明底 PNG，不需要再跑抠图模型。贴纸、素材、电商图从两道工序变一道。
- **最多 10 张参考图**。画布的「图生图」节点本来就允许多连，`ai.ts` 里已经是
  `body.image = refs.map(fileToDataUrl)`，**开箱就能吃到 10 图**，不用改渲染层。
- **原生 2K + 编辑一体**。2048×2048，16:9 长边可到 2752。同一个权重做生成和编辑。

代价是文本编码器极重：借用 **Qwen3-VL-8B**，单个组件 17.5 GB，比主干还大。
这是必须开 `enable_model_cpu_offload()` 的原因——编码完前几步它就没用了，挪回内存，
峰值从 40 GB 降到 22 GB，省下来的 18 GB 正好养着语音。

**默认档位**（`deploy/.env` 可调）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `YJ_IMAGE_STEPS` | 28 | 官方标准 40 步；28 步在 2K 下肉眼难分，快 30% |
| `YJ_IMAGE_MAX_SIDE` | 1536 | 长边上限。改 2752 才是原生 2K，慢 3–4 倍、显存 ×4 |
| `YJ_IMAGE_OFFLOAD` | 1 | **必须为 1**，否则和语音抢不过来 |

4090D 上 1536px / 28 步大约 **15–25 秒**一张（含 offload 的换入换出）。
1024² 会更快，约 8–12 秒。

### 2. 语音：Qwen3-TTS-12Hz-1.7B 三件套

你现在的代码已经是三档结构（`vendor/voice/app/server.py` 里 `custom / base / design`），
**升级到 1.7B 只需要把权重换掉，Python 一行不用改**：

| 目录 | 权重 | 能力 |
|---|---|---|
| `qwen-tts-custom` | 1.7B-CustomVoice（3.9 GB） | 9 个预设音色 + 自然语言风格指令 |
| `qwen-tts-base` | 1.7B-Base（3.9 GB） | 3 秒参考音频零样本克隆 |
| `qwen-tts-design` | 1.7B-VoiceDesign（3.9 GB） | 用文字描述「捏」一个音色 |
| `qwen-tts-tokenizer` | 12Hz Tokenizer（0.68 GB） | 三个都要用，必需 |

为什么值得从 0.6B 换上来：**自然度约 +23%，情感表达和长句连贯性明显更好，而且
VoiceDesign 只有 1.7B 有。** 显存从 4 GB 涨到 6 GB，现在的编排里挤得下，不值得为这 2 GB 退回去。
0.6B 保留作降级（改目录内容即可）。

已有能力不受影响：预设音色试听样本、克隆后自动生成预览、行内改名（PATCH 只改 name 不动 id）、
音频节点连角色卡自动取音色——这些都在渲染层，跟模型大小无关。

**权重放对了不代表能合成 —— 语音链的 Python 依赖是独立的一套，`init.sh` 第 2b 步专门装它。**

这一块最容易踩的坑是：引擎进程起得来、`/healthz` 回 200、`/.well-known` 报
`models: {custom:true, base:true, design:true, asr:true}`，看着全绿，
**一点「合成」立刻 500**。原因是依赖缺失被引擎的懒加载掩盖了 —— 它在真正
`import qwen_tts` 之前不会碰这些包。

必须装齐的（缺一个就是 500，而且报错各不相同）：

| 包 | 缺了会怎样 |
|---|---|
| `qwen-tts`（**`--no-deps`**） | `ModuleNotFoundError: qwen_tts` |
| `pylibs/tf4` 里的 `transformers==4.57.3` + `tokenizers==0.22.1` + `huggingface_hub<1.0` | `tokenizers>=0.22.0,<=0.23.0 is required ... found 0.23.3` |
| `sox`（pip）**和** `sox`（apt，系统包） | `ModuleNotFoundError: sox` |
| `onnxruntime` | `ModuleNotFoundError: onnxruntime`（VQ 模块要用） |
| `einops` | `ModuleNotFoundError: einops` |
| `torchaudio`（版本**必须与 torch 一致**） | `ModuleNotFoundError: torchaudio` |
| `sherpa-onnx` | 转录节点不可用，克隆退到 x-vector 模式（音色像、韵律弱） |

两处版本隔离是硬要求，不是可以「统一一下」的：扩散链要 `transformers 5.x + hub 1.x`，
语音链要 `4.57.3 + hub 0.x`。往任一边靠，另一边立刻挂。所以主 venv 永远保持 5.x，
4.x 装进 `pylibs/tf4`，由 `voice-server/server.py` 在 import 前
`sys.path.insert(0, ...)` 注入。

自查一行（在 `voice-server` 同级的 venv 里跑）：

```bash
python -c "import sys; sys.path.insert(0,'pylibs/tf4'); import qwen_tts; print('ok')"
```

真实验证不要只看 `/healthz`，要发一次合成：

```bash
curl -s -X POST http://127.0.0.1:6006/api/rpc -H 'content-type: application/json' \
  -d '{"ns":"voice","method":"speak","args":[{"text":"测试","voiceId":"preset:Vivian","speed":1}]}' \
  -o /tmp/sp.json -w '%{http_code}\n'
# 期望 200，且 /tmp/sp.json 里有个 .wav 路径；169 KB ≈ 3.5 秒 24 kHz 单声道
```

**实机实测（1.7B bf16 / cuda:0，2026-10-23）**：

| 动作 | 耗时 | 备注 |
|---|---|---|
| 模型加载 | 7–17 s | 首次 / 空闲 15 分钟卸载后重载 |
| 预设音色合成 | 28 字 → 5.04 s 音频，**6–8 s** | 24 kHz 单声道 WAV |
| 克隆建库 | **1.0 s** | 只存参考音频 + 转写，不做 embedding |
| 克隆音色合成 | 15 字 → **15.5 s** | 比预设慢，因为要多跑一遍 ICL |
| 转录（SenseVoice int8） | 5 秒音频 → **0.4 s** | 中文准确，同音字会有偏差（「艺镜」→「意境」） |

两个实测才知道的点：

- **`Qwen3-TTS-Tokenizer-12Hz` 其实不用单独下**。1.7B 的 `CustomVoice` / `Base` 目录里
  自带 `speech_tokenizer/`，`Qwen3TTSModel` 会按 `speech_tokenizer/config.json` 自己找。
  `bootstrap.sh` 仍然会下一份 0.68 GB 作兜底（某个子模型目录里没带时不至于临时报错），
  不影响正确性，只多占一点磁盘。
- **参考音频的转写决定克隆质量**。`generate_voice_clone` 默认走 ICL 模式，没有
  `ref_text` 会直接抛 `ValueError: ref_text is required when x_vector_only_mode=False`。
  所以「SenseVoice 装没装」不是转录节点的附属问题，而是克隆能不能用的前置条件——
  没装时 `server.py` 会退到 `x_vector_only_mode=True`（音色像、韵律弱），
  而不是让整次合成立刻失败。

### 3. 视频：MiniMax H3-Base

**音画一体**是它相对 Wan 的本质差别：768p / 24fps / 原生立体声，一个模型同时出画面和声音，
不用另外跑一遍 TTS 再对齐。这对短剧工作流是实打实的省事。

规模也确实是另一个量级。下表的「量化」一列是 `DiffSynth-Studio/MiniMax-H3-NF4` 的
**实测文件体积**（2026-10-24 逐文件量的，不是估算）：

| 组件 | 全精度（官方 bf16） | NF4 量化包（实测） |
|---|---|---|
| Transformer（33B） | 66.3 GB | 17.16 GB（`minimax-h3-fl2va-nf4`） |
| 文本编码器（Qwen3-VL-32B） | 51.5 GB | 15.32 GB（`text-encoder-nf4`） |
| 视频 VAE + 音频 VAE | 5.8 GB | 1.61 + 0.28 GB |
| 分词器 / processor | — | 11 MB（在官方仓库的 `FL2VA/processor/`） |
| **合计** | **123.6 GB** | **34.4 GB** |

**官方 bf16 的 FL2VA 分区实测 136 GB（按 1024 算是 127 GiB），48 GB 的卡连显存带内存都放不下**，
所以一律走 NF4。
NF4 那 34.4 GB 是**只收 FL2VA 这一路**的结果：同一仓库存了 5 个大分片共 72.5 GB，
`ref2va-*` 和两个 `-pruned-` 版属于另一条管线，全收白占 38 GB。

实测速度参考（社区 + 官方口径，2026-10）：

| 配置 | 设置 | 一条 5 秒 |
|---|---|---|
| 4× H100 80G | BF16 / SGLang / 50 步 | 200 秒（1344×768） |
| 32G RTX 5090 | FastH3 V2 NVFP4 | 38.6 秒（1344×768） |
| 24G RTX 4090 | FastH3 V2 FP8 | 154.6 秒（1344×768） |
| 12G + 32G RAM | Base / SGLang 消费级配方 / 20 步 | 319–356 秒（864×480） |

**这台 4090D 24G 的预期：NF4 + disk offload、1344×768，约 3–6 分钟一条 5 秒**
（比表里 154 秒那条慢，是因为量化包要往内存/磁盘换出层，不是算力差）。
48 GB 以上的卡不需要 offload，同一条能压到 2–3 分钟。

H3 不是"纯云端黑盒"了，但要清楚没开源的两块：`H3-Context-IR`（多模态上下文理解）
和 `H3-Regenerate-2K`（升 2K）。**本地能出 768p 带声音的片段，拿不到官方那条 2K 重生成链路。**
需要 2K 成片时还是得走云端 API——这也是建议保留双通道的原因。

### 3.1 部署时踩到的三个硬坑（2026-10 实测）

这三个坑不写下来，下一次重装还会原样再踩一遍。

**① 官方仓库是 bf16 全量，谁都别想直接跑。**
`MiniMaxAI/MiniMax-H3` 的 `FL2VA` 分区实测 **136 GB**（transformer 62 GB + Qwen3-VL-32B
文本编码器 63 GB + 视频 VAE 9.8 GB），要 125 GB 显存。这台机器 24 GB 显存 / 56 GB 内存，
两个主件加起来就超过内存，全量 CPU offload 也放不下。**能跑的是 NF4 量化包**
（`DiffSynth-Studio/MiniMax-H3-NF4`，FL2VA 路线 34.4 GB），不是这个官方 bf16 仓库。
所以 `bootstrap.sh models video` 默认下 NF4；官方全量必须显式点名 `models video-full`，
连 `models all` 都不会带上它（`take()` 里对 `video-full` 单独判）。

**② 官方包的 `model_index.json` 是老格式，现在的 diffusers 认不出来。**
该文件写的是 `_class_name: MiniMaxH3Pipeline`，但 diffusers 0.41 里真正的类是
`MiniMaxH3ModularPipeline`（模块化管线，blocks 是 `MiniMaxH3Blocks`）。直接
`from_pretrained` 会报三种错，一路试过去是这样：

```
ModularPipeline.from_pretrained(dir)
  → AttributeError: module diffusers has no attribute MiniMaxH3Pipeline
MiniMaxH3ModularPipeline.from_pretrained(dir)
  → ValueError: No pipeline blocks could be resolved ...
ModularPipeline(pretrained_model_name_or_path=dir, blocks=MiniMaxH3Blocks())
  → AttributeError: module transformers has no attribute MiniMaxH3Qwen3VLHFEncoder
```

第三条说明它还要求一个带 `MiniMaxH3Qwen3VLHFEncoder` 的 transformers 版本
（本机 5.20.2 没有）。**结论：官方 bf16 路线在当前环境下走不通，不是缺一行代码的事。**

**③ NF4 包没有 `model_index.json`，一切「入口文件存在性」判据都得放宽。**
它是扁平结构：根下是 `configuration.json` + 几个 `*_nf4.safetensors`。
以前 `model-server._has_weights()` 和 `web/host.mjs` 的 `entryFile()` 只认
`model_index.json`，于是**装齐了也报 missing**。现在两个都改成「命中任一」。

所以「视频在这台机器上能不能跑」的答案是 **能，只是慢**：

- **NF4 量化包**（默认下的那份）：官方 README 口径「最低 8 G 显存即可运行」，
  靠 disk offload 把用不到的层换出去。24 G 的 4090 是能出片的，5 秒 768p 约 3–6 分钟。
- **官方 bf16 全量**：125 GB 显存，这台别想。下它只有一个结果：占 171 GB 磁盘 +
  内存被 offload 打满，最后 OOM。

装视频（34.4 GB，落云盘，不进镜像）：

```bash
bash deploy/bootstrap.sh models video     # 或者直接在「配置检测」面板上点下载
bash deploy/run.sh restart
```

`run.sh` 的 `pick_video` 会按目录形态自动把 `YJ_VIDEO_MODEL` 指对（NF4 扁平包指根目录、
官方分区指 `FL2VA/`），`video_worker.py` 再按路径里的 `nf4` 字样先走 `h3_diffsynth`。
两处都不需要手改配置。启动时它还会打一行实话：盘上没有权重就说「未安装」，
有 NF4 但卡太小才提显存门槛 —— 不会再对着一张能跑的卡报「生视频会失败」。

> 以前这里有一档 `Wan2.2-TI2V-5B`（32 GB 权重 / 20 GB 显存，24 GB 卡能跑），
> 作为小显存机器的降级档。它已经不在了 —— 理由写在 `deploy/video_worker.py` 入口：
> **「悄悄换个模型给你出片」比「直说这个模型不支持」有害得多**，
> 用户会以为自己用的是 H3，实际拿到的是 5B 的效果。

### 3.2 权重全放云盘：代价是首轮冷读，好处是镜像只有 9 G

`/root/cloud` 是 webdav。放这里的好处是不进镜像、重开实例还在；
代价是**每次开机后第一次加载都要从网络读全量权重**——实测冷读 30 GB 级的权重目录要十几分钟
（7–15 MB/s，而系统盘 `/root/models` 量到 67 MB/s 以上），
而预热之后（进 page cache）同样的加载只要几十秒。

这个取舍是明确的：**镜像里一份权重都不放**（上限 30 G，实测 9.0 G），
代价只是每个模型当天第一次用慢一点。实测语音 13 G 从 webdav 加载后合成
`200 / 6.9 秒 / 24 kHz` —— 首次慢，之后正常。

内存 56 GB 装不下 图片(31) + 文本(16) + 视频(34) + 语音(13) = 94 GB 的全部缓存，
所以**同一时间只热一个模态**是常态，这也是 `model-server` 用显存租约编排的原因。

真要让某个模型「开机秒用」，把它拷到 `/root/models`（系统盘还有 ~100 G 余量），
`pick_model` 会自动优先选系统盘那份 —— 但**存镜像前必须删掉**，否则镜像立刻超 30 G。

这个镜像的说明页里明确写了一行**「应用及模型请部署安装在 `/root/` 目录下」**——所以代码放 `/root/`，
模型放 `/root/cloud/`（云储存，不进镜像、重开实例还在，9 G 的镜像不会被 94 GB 模型撑爆）。
`bootstrap.sh` 探测持久盘的顺序已经把 `/root/cloud` 排在第一位。


#### 为什么不能用 ComfyUI 镜像

这套方案**明确不要 ComfyUI**，那层壳对我们只有负担。更要命的是它会把环境弄脏：

1. **`diffusers` 被锁在旧版**。Qwen-Image-2.1 的 pipeline 是 2026-09 才合进 diffusers 的，
   我们要 `>=0.36`。在 ComfyUI 镜像里 `pip install -U diffusers` 会连带升级一串依赖，
   把镜像作者调好的依赖树打乱，典型报错是 `cannot import name ... from diffusers.utils`。
2. **`python3` 常常不是你以为的那个**。这类镜像多用 miniconda，`python3` 指向系统 python，
   而 `pip` 指向 conda。结果就是「明明装了 `qwen-tts`，却报 ModuleNotFoundError」——
   这个问题能查一下午。
3. **`transformers` 被 custom_nodes 绑着**。我们要 `>=4.60`（Qwen3-VL 编码器需要），
   升上去会让镜像里某些节点报废。我们不用那些节点，但报错会把你引到错误的方向。
4. **省不下的时间会还回去**。省的是「装 torch 的 5 分钟」，赔的是排查依赖冲突的两小时。

#### 开机器时的参数

| 项 | 值 | 原因 |
|---|---|---|
| GPU | **RTX 4090 24 GB 起**（48 GB 更好） | 24 GB 走 NF4 + disk offload 能出片，一条 5 秒 3–6 分钟；48 GB 不需要 offload，压到 2–3 分钟。**不要再买 48 GB 只是为了「能跑」** |
| 系统盘 | ≥ 30 GB | 依赖 + 临时文件；系统盘只装代码和环境，权重一律进云盘 |
| 数据盘 | **≥ 120 GB** | 模型 94 GB + 产物 + 余量；官方全量 H3 则要 300 GB |
| 端口 | 6006（部署后加进端口映射） | 静态、API、文件、SSE 全走这一个端口 |
| 计费 | 按分钟 | 关机即停，但**数据盘通常仍计费**，别以为关了就全免 |

> **48G 卡经常缺货**（`RTX 4090D 48G` 显示「暂无可用」是常态，¥2.59/时），
> 而隔壁 `RTX 4090 24G` 是 ¥1.89/时、反而有货。
> **现在不需要为了出视频去等 48G**：24G 装 NF4 就能出片，只是慢一档。
> 等 48G 有货再迁也可以 —— 代码和 `.env` 原样拷过去、模型目录一并搬即可，两边通用。

> 数据盘要挂成持久盘。`bootstrap.sh` 会按 `/root/cloud → /root/xgpu-tmp → /data → /workspace
> → /root/autodl-tmp` 的顺序探测并把结果写进 `.env`，之后不再变——但如果平台把数据盘挂在别处，
> 第一次 `status` 时要留意它打印的路径，那才是模型真正住的地方。

**第三条如果返回 `False`**，说明镜像里的 torch 是 CPU 版，或者 CUDA 版本和驱动不匹配。

用 `--system-site-packages` 让 `.venv` 直接复用镜像里这个 torch。想强制重装一遍：`YJ_FRESH_TORCH=1`。

> 唯一的风险：万一新版 `diffusers` 要求 `torch >= 2.6`，复用 2.5.1 会在 import 时报版本不够。
> 这时别换镜像，直接升 torch——驱动是向前兼容的，镜像写「CUDA 12.4」只是 toolkit 版本：
> ```bash

> ```
> 还报错就退回 cu124 的 2.6.0：`... /whl/cu124`。两条都不行才考虑换镜像。

#### 如果已经开了 ComfyUI 镜像，要重开吗

不用。`bootstrap.sh` 会建**独立的 `.venv`**，不碰系统环境，所以 ComfyUI 镜像也能跑起来。
只是多承担上面第 1、2 条依赖冲突的风险。**能跑，但没必要冒这个险**——新开一台干净的更省事。

#### 救急用的社区镜像（不是本方案路线）

### 第 2 步：本地打包上传

```bash
cd /path/to/yjai-studio
npm run build:web        # 产出 dist-web
npm run pack:cloud       # 产出 release-web/yjai-deploy.tgz（约 2.5 MB）
scp release-web/yjai-deploy.tgz root@<实例>:/root/
ssh root@<实例> 'cd /root/yjai-studio && tar xzf ../yjai-deploy.tgz'
```

`pack:cloud`（`scripts/pack-cloud.mjs`）不是简单打 tar，它做三件必要的事：

1. **硬排本机数据**：`deploy/model-data`、`probe_*.py`、`__pycache__`、`*.log`、`.webdata`
   一律不进包 —— 曾经把本机的 `video.log` 和 5 个探测脚本带上线。
2. **路径一律相对 cwd**：Windows 的 tar 会把 `F:` 当成远程主机，`-T` 直接报 status 2。
3. **打完自检**：`tar tzf` 扫一遍命中禁用规则就**退非零**；`.sh` 里有 `\r` 也退非零
   （CRLF 的脚本在 Linux 上会报 `set: pipefail: invalid option name`，看着像语法坏了）。

不需要上传 `node_modules`，服务器端只跑 `web/host.mjs`（零依赖）。

### 第 3 步：装环境（只做一次，做完立刻保存镜像）

```bash
export HF_ENDPOINT=https://hf-mirror.com
bash deploy/bootstrap.sh install --with-models
```

装的东西：Node 20、ffmpeg、Python venv、torch cu124、`diffusers>=0.36`（旧版不认
Qwen-Image-2.1 的架构）、`transformers>=5.0`（Qwen3-VL）、`qwen-tts`（`--no-deps`）、
`pylibs/tf4`（语音专用的 transformers 4.x 副本，约 240 MB）、`sherpa-onnx`（SenseVoice）、
`soundfile`、`huggingface_hub[cli]`，以及可选的 `bitsandbytes` / `torchao`（量化用）。

> **`diffusers` 版本是这一版最容易踩的坑之一**：老版本 `from_pretrained` 一个 7B 单流 DiT
> 会报「不认识的架构」，看起来像模型下坏了。
>
> **另一个坑更隐蔽：`qwen-tts` 和 `diffusers` 对 transformers 的要求互相矛盾。**
> diffusers 0.41 要 5.x（`huggingface_hub` 要有 `resolve_revision`），
> qwen-tts 0.1.1 要 4.x（5.x 里 `check_model_inputs` 从工厂函数变成了直接装饰器，
> `PretrainedConfig` 的属性访问也变严了）。往同一个环境里硬装的结果是二选一：
>
> ```
> 装完语音 → 出图报 cannot import name 'resolve_revision'
> 修好出图 → 语音报 check_model_inputs() missing 1 required argument
> ```
>
> 所以 `bootstrap.sh` 里 qwen-tts **一律 `--no-deps`**，另外把 4.x 那份单独装到
> `pylibs/tf4`，由 `voice-server/server.py` 启动时 `sys.path.insert(0, ...)`。
> 只多 240 MB —— 比再装一份 torch（7 GB）划算得多，而且这机器系统盘总共只用 9 G（上限 30 G）。

### 第 4 步：下模型（约 94 GB，1–3 小时）

**别用 `models all` 无脑下。** 先看第零节的显存结论，或者直接把 `--want` 交给它
（`bootstrap.sh` 的 `want` 默认就是 `auto`，会自己读显存）：

```bash
bash deploy/bootstrap.sh models            # auto：按这台机器的显存决定装哪些
bash deploy/bootstrap.sh models image voice # 或者按 key 逐个装
```

| 项 | 仓库 | 体积 |
|---|---|---|
| 图片 | `Qwen/Qwen-Image-2.1` | 31 GB |
| 视频 | `DiffSynth-Studio/MiniMax-H3-NF4` + 官方仓库的 `FL2VA/processor/` | **34.4 GB**（FL2VA 四件；官方 bf16 全量 171 GB 要显式点名 `models video-full`） |
| 文本 | `Qwen/Qwen3-8B-Instruct` | 16 GB |
| 语音 | `Qwen/Qwen3-TTS-12Hz-1.7B-*` × 3 + Tokenizer | 13 GB |

权重默认落 `/root/cloud/models`（webdav，**不进镜像**）。也可以不跑这条命令，
直接在画布的「配置检测」面板上点每一项的「下载」—— 走的是同一个宿主进程下载器，
落盘位置、断点续传、清单校验都一样。

**H3 可能需要同意许可**：如果报 `gated` / `401` / `403`，去模型页点同意，
然后 `hf auth login` 填 Access Token，再重跑这一条。

### 第 5 步：装开机自启 + 起服务 + 开端口

**先装自启，再起服务。** 顺序反过来就会出现「这次能开、下次开机网页打不开」：

```bash
bash deploy/install-autostart.sh     # 注册钩子并立刻起一次（幂等，可反复跑）
bash deploy/bootstrap.sh status      # 确认四进程 / 每个模态 ready / 实际显存
```

`install-autostart.sh` 按宿主机的实际情况注册，命中哪个用哪个：

| 机制 | 什么时候用 | 落点 |
|---|---|---|
| `/scripts/start.d/` | **仙宫云容器**（PID 1 是 `docker-init -- /scripts/start.sh`） | `start.d/50-yjai.sh` |
| systemd | 真有 systemd 的云主机（判据是 `/run/systemd/system` 存在） | `yjai-studio.service` |
| `/etc/rc.local` | 有 sysvinit 的镜像兜底 | `/etc/rc.local` |

三者都只转调 `deploy/autostart.sh`，所以**启动逻辑只有一份**。`autostart.sh` 自己会先等
`/root/cloud` 挂上（权重在 webdav，云盘挂载比容器启动慢；`run.sh` 是按目录存在性选模型
路径的，云盘没挂上会指到一条不存在的路径，之后即使挂上也认不回来），再调幂等的
`run.sh start`，最后探一次 6006 把结果写进 `/var/log/yjai-autostart.log`。

> **这里踩过一个很贵的坑，值得写下来。** 旧版 `init.sh` 只写 systemd 服务，
> 而这台容器的 PID 1 不是 systemd：`systemctl daemon-reload` 返回非 0，
> 而 `init.sh` 开头是 `set -e` —— 脚本在**自启那一步就中断了**，后面
> 「启动服务」从来没执行过。表现正是「部署脚本跑完了，6006 一直是空的，网页打不开」，
> 手动 `run.sh start` 立刻就通。后来补写 `/etc/rc.local` 也没用 —— 没有 init 会去读它。
> 现在 `install-autostart.sh` 不用 `set -e`，三档注册各判各的，不会再因为一个机制不适用就全盘失败。

`status` 会打印三件事：四个进程是否活着、`/healthz` 里每个模态是 ready 还是 down、
以及 `nvidia-smi` 的实际显存占用（比任何估算都准）。

然后在仙宫云控制台把 **6006** 加进端口映射，浏览器打开给的地址就是画布。
静态资源、API、文件直链、SSE 全走这一个端口，不需要第二个。

> **这一条只能在控制台点，容器内改不了。** 实测容器里没有任何「自定义服务」注册文件：
> `/.xgcos/.links` 只是缩略图缓存，`/scripts` 只有 `start.sh` + `start.d/`，
> `xgc-container-agent` 是平台侧 agent。公网网关格式是 `<机器id>-<端口>.x-gpu.com`，
> **未登记的端口一律回 502**（连 jupyter 的 8888 也是 502），登记后才通。
> 所以「自定义服务」里那条「艺镜AI无限画布（6006）」需要你在实例页手动加一次。
> 加完以后桌面快捷方式（`/.xgcos/desktop/yjai.app`）和这个入口指向同一个服务。

## 四、客户端怎么接

在「设置 · 通道」里新建一个 **「自建 / 本机（OpenAI 兼容）」**，填：

按**目录形态**解析，最终 `YJ_VIDEO_MODEL` 指向真实存在的那一份。

## 八、成本与时序

**仙宫云按开机时长计费，所以真正决定成本的是两件事：关机习惯，和镜像大小**
（镜像体积影响保存与开机拉取，也是实打实的钱）。

按当日价（`RTX 4090 24G` ¥1.89/时，`RTX 4090D 48G` ¥2.59/时；单价以控制台为准）：

| 场景 | 耗时 | 算力成本 |
|---|---|---|
| 一张 1536px 图 | 15–25 秒 | ¥0.01 |
| 一条 5 秒 768p H3 NF4（带声音，24 G 卡 + offload） | 3–6 分钟 | ¥0.10–0.20 |
| 一条 5 秒 768p H3 NF4（48 G 卡，无 offload） | 2–3 分钟 | ¥0.09–0.13 |
| 一天重度用 4 小时（24 G） | — | ¥7.6 |

**最贵的不是算力，是忘记关机。** 空跑 24 小时 = ¥45，够你出一周的图。
建议把 `bootstrap.sh stop` 挂到平台的关机脚本上。

镜像这边要守住一条线：**系统盘 ≤ 30 G，权重一律不进镜像**。
实测清理后 9.0 G（系统 7 G + `/usr` 4.5 G + `/opt/node20` 2.3 G + 项目 1.2 G + miniconda 787 M，
有重叠所以合计小于逐项相加）。清理前是 23 G —— 差的 14 G 全是躺在系统盘上的模型权重，
删掉之后功能一点没少，因为它们本来就在云盘上重新下得回来。

**点「保存镜像」之前跑这四条**（数不对就别存，存下去白花钱）：

```bash
df -h / | tail -1                        # 已用应 ≈ 9 G，超过 30 G 先查是谁占的
du -shx /root 2>/dev/null | tail -1      # 应 ≈ 9 G（代码 + .venv + node）
[ -d /root/models ] && echo "⚠ 系统盘上有权重，删掉再存" || echo "OK：权重不在系统盘"
# 自启钩子必须在镜像里，否则换台机器开出来还是打不开网页
[ -x /scripts/start.d/50-yjai.sh ] && echo "OK：容器钩子在" || echo "⚠ 跑 install-autostart.sh"
```

> 最后一条容易被忽略：`/scripts` 和 `/etc/rc.local` 都在镜像层（只有 `/scripts/start.sh`
> 是平台只读挂载），所以钩子写得进去也会跟着镜像走。**但项目目录被删或挪走，钩子就空转** ——
> `autostart.sh` 第一行是 `[ -d "$ROOT/deploy" ] || exit 0`，它不会报错，也不会起服务。

一次性时间投入：装环境 30–60 分钟，下模型 1–3 小时（取决于带宽），
之后每次开机到能用 **约 1 分钟**——前提是第 3 步做完立刻**保存自定义镜像**。
不存镜像，每次重开都要重装一遍，那"开机就能用"就是空话。

## 九、已知风险与降级路径

| 风险 | 表现 | 处理 |
|---|---|---|
| diffusers 没有 Qwen-Image-2.1 的 pipeline | `ImportError: QwenImagePipeline` | `pip install -U diffusers`；代码已经做了类名探测（4 个候选） |
| H3 在 diffusers 里还没合入 | 「H3 后端都不可用」+ 两个具体错误 | 走 NF4 + DiffSynth（默认路线）；实在不行 `YJ_VIDEO_BACKEND=sglang`，或 `cmd` 配一条命令行 |
| 权重装齐了但检测报 missing | 面板「未就绪 · 找不到权重」 | 先看 `entry` 是不是只认 `model_index.json` —— NF4 是扁平包，认的是 `configuration.json` |
| H3 权重 gated | `401 / 403` | 模型页同意许可 + `hf auth login` |
| 出图 OOM | 加载时爆显存 | 先降到 1024²，或装 `bitsandbytes` 走 INT8（全套约 14 GB） |
| 出视频 OOM | 提交后子进程崩 | 确认语音已让位（`/unload` 返回非空）；降 `--steps` 到 30、分辨率 832×480 |
| 出视频极慢 | 5 秒要十几分钟 | 24 G 卡是 disk offload 在换页，属预期；要快换 48 G 卡（同一条 2–3 分钟） |
| 开机首轮加载慢 | 图片/视频第一次点要等几分钟 | webdav 冷读 7–15 MB/s，属预期；预热之后正常。要彻底解决就把该模型拷到 `/root/models`，但**存镜像前删掉** |
| 镜像超 30 G | 保存时体积暴涨 | 存镜像前 `du -shx /root/models` 应为 0（不存在）；权重只该在 `/root/cloud` |
| 原生 2K 出不来 | 设置 2752 后极慢或 OOM | 24 G 卡上 2K 建议只做单张精修；批量走 1536 |
| 视频导出没声音 | 成片无声 | 有音频轨但没 `ffmpeg`；`apt-get install -y ffmpeg` |
| 开机后 6006 打不开 | 外网 502/超时，`ss -lnt` 里没有 6006 | 先 `bash deploy/run.sh start`：能起来就是**自启没装**（跑 `install-autostart.sh`）；起不来再看它打印的哪一项失败 |
| 自启钩子在但服务没起 | `/var/log/yjai-autostart.log` 没新内容 | 钩子第一行要求 `$ROOT/deploy` 存在；项目目录搬过就重跑 `install-autostart.sh` |

## 十、下一步建议（按收益排）

1. **先把图片链路跑通**（收益最大、依赖最少、15 秒一次反馈）。图片能出，说明
   通道、RPC、文件直链、画布存盘整条链路都是通的。
2. 再跑语音（换权重即可，风险最低）。
3. 最后跑 H3（最重、生态最不稳，留到最后不怕返工）。
4. 图片节点的 UI 加一个「透明背景」勾选框 —— 后端 `transparent` 已经通了，
   现在只差一个 checkbox，贴纸工作流就闭环了。
