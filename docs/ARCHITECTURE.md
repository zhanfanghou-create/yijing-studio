# 架构说明

> 这份文档解释「为什么这么写」，不是 API 手册。代码以混淆形式发布，
> 所以这里用文字和结构图把关键取舍讲清楚 —— 想改的人能看懂骨架，想审计的人能对上行为。

---

## 1. 整体分层

```
┌─────────────────────────────────────────────────────────────┐
│  渲染层（Chromium）                                           │
│  React 18 · @xyflow/react 12 · zustand 4                      │
│                                                              │
│  shell/      顶栏、侧栏、设置、配置检测、命令面板               │
│  canvas/     画布、节点、编辑面板、工具箱、时间轨               │
│  store/      docStore（文档）· settingsStore · uiStore         │
│  services/   生成链路、导出、波形、缩放                        │
│  agent/      工具定义、能力模式、系统提示词                    │
└──────────────────────────┬──────────────────────────────────┘
                           │  window.yj.*（contextBridge）
┌──────────────────────────▼──────────────────────────────────┐
│  主进程（Node）                                               │
│  ipc/ai          模型请求唯一出口（回环地址硬校验）             │
│  ipc/modelInstall 下载 / 续传 / 进度 / 测速                    │
│  ipc/backend     服务自动拉起（TCP 探活 + 10s 缓存）           │
│  ipc/export      ffmpeg 拼片                                  │
│  ipc/voice·sr·storage·system·assets·comfy                     │
└──────────────────────────┬──────────────────────────────────┘
                           │  HTTP 127.0.0.1
┌──────────────────────────▼──────────────────────────────────┐
│  本地推理（Python）                                            │
│  8001 对话 · 3911 媒体（图 / 视频 / 超分）· 3910 语音           │
└─────────────────────────────────────────────────────────────┘
```

渲染层与主进程之间没有隐式通道：所有跨进程能力都显式挂在 `window.yj` 上，
按域分组（`ai`、`model`、`system`、`voice`、`sr`、`storage`…）。
这条边界让「渲染层能干什么」可以被一次性审完。

## 2. 文档模型：一个 store，一次 commit

整个画布（节点 + 连线 + 设置 + 记忆）是一个 `CanvasDocument`，存在一个 zustand store 里。

**所有修改都走同一个 `commit(fn, opts)`：**

```ts
commit((doc) => ({ ...doc, nodes: next }))
```

这么做换来两件事：

1. **撤销栈天然一致。** 不依赖组件状态，不依赖 React 的批处理时机，
   每一步都是完整的文档快照（`MAX_HISTORY = 80`）。
2. **批量操作的粒度可控。** 顶栏「参数」一次要改画布上所有视频节点，
   如果循环调 `updateNode`，20 张卡就是 20 步撤销 —— 用户按一次 Ctrl+Z 只退掉一张，
   和「一次操作」的直觉不符。所以有 `updateMany`，合并成一次 commit。

### 连续输入：history 是可选参数

时间轨、拖拽这类高频输入会在一秒内触发几十次修改。如果每次 commit 都压栈：

- 撤销栈被一次拖动挤满（80 格只够拖两次）
- 用户按 Ctrl+Z 要按几十下才退得回去

所以拆成两个方法：

| 方法 | 写历史 | 用途 |
| --- | --- | --- |
| `updateNode` / `updateMany` | 是 | 一次性操作 |
| `updateNodeLive` / `updateManyLive` | 否 | 拖动过程中的实时写入 |
| `pushHistory()` | 压一条快照 | 拖动**第一次真的变化之前**调一次 |

控件的写法是固定的三步：

```ts
onGrab   → pushHistory()          // 值还没变，快照是拖动前
onChange → updateNodeLive(...)    // 一路静默写
onUp     → 什么都不用做           // 历史已经只有一格
```

真机上验证过：把时长从 14s 拖到 17s 再拖到 29s，按两次 Ctrl+Z 精确回到 17s、14s，
而不是回到中间的某个值。

## 3. 画布：React Flow 的用法

用的是 `@xyflow/react` 12，没有自己造画布引擎。基于它做了这些：

| 能力 | 做法 |
| --- | --- |
| 网格背景 | 原生 `<Background>`，不用自己画 CSS 网格 |
| 小地图 | 原生 `<MiniMap>` |
| 落位吸附 | `snapToGrid` + `snapGrid=[12,12]` |
| 连线校验 | `isValidConnection` → `canLink(from, to)` |
| 对齐辅助线 | 拖动时比对邻居节点的四边与中线 |
| Alt + 拖拽复制 | `onNodeDragStart` 里判断 `altKey` |
| 快捷键 | 画布外统一监听，按 `document.activeElement` 判断是否在输入框里 |

### 连线矩阵

哪些节点能连哪些节点，是一张显式的矩阵，不是「随便连、出错再说」。
两个维度：

- **节点类型级**：角色卡只能连剧本 / 视频 / 分镜，不会出现无意义的线。
- **端点级**：资源节点（素材库）的入度恒为 0，某些节点只做源不做目标。

两层分开是因为矩阵表达不了「入度恒为 0」这种约束。
`canLink` 管前者，`canLinkEndpoints` 管后者，界面走后者。

### 连线不是装饰

连线在文档里是有语义的 `role`：

| role | 含义 |
| --- | --- |
| `prompt` | 上游文本注入下游提示词 |
| `reference` | 上游作为参考图 / 参考素材 |
| `audio` | 上游音频作为下游音轨 |
| `structure` | 上游进入下游的清单（角色集、成片顺序） |

`structure` 类的连线会真的改下游数据：视频连到成片预览会进「镜头顺序」，
角色连到角色集进「角色清单」，断线就摘掉。这是「连线有用」的具体含义。

## 4. 能力表：表单是推导出来的

`capabilityOf(model, kind)` 返回：

```ts
{
  maxRefs: number          // 参考图上限，0 = 不支持
  ratios: string[]         // 可选画幅
  resolutions?: string[]   // 可选清晰度
  defaultResolution?: string
  supportsFirstLastFrame?: boolean
  supportsAudio?: boolean
}
```

界面据此收缩选项。好处是**永远不会发出上游必定拒绝的请求**，而且模型一切换，
选项跟着变 —— 这是推导，不是三处手写枚举然后忘了改一处。

### 时长为什么不在能力表里

0.1.0 把视频时长从「按模型枚举几档」改成了 **1–30 秒整秒连续可选**：

- 云端模型按「档位」计费，所以只开放离散值；
- 本项目跑本地推理，服务按 `duration × 24` 算帧数，任意整秒都能生成。

所以时长的口径从 `capabilityOf().durations` 挪到了模块级常量
`VIDEO_DURATION_MIN / MAX` + `clampDurationSec()`。
生成前仍然会裁剪一次，但只裁到 1–30 的硬区间，不再按模型档位偷偷改回 5 秒。

`cap.durations` 字段保留着，作为「模型原生档位」的元数据。

## 5. Agent：能读能写，但只能通过工具

创作助手不是「把画布 JSON 塞进提示词让模型自由发挥」，而是一组显式工具：

| 工具 | 作用 |
| --- | --- |
| `inspect_document` | 读当前画布（节点、连线、问题、选中） |
| `create_node` | 建节点 |
| `update_node` | 改字段 |
| `delete_nodes` | 删节点 |
| `connect_nodes` | 连线（走同一套 `canLink` 校验） |
| `add_shots` | 给分镜板补镜头 |
| `generate` | 触发某个节点的生成 |
| `remember` | 写项目记忆 |
| `report_issue` | 在节点上报错 |
| `focus` | 把视口移到某个节点 |

**能力模式**是追加到系统提示词的一段行为约束：

| 模式 | 约束 |
| --- | --- |
| 综合助手 | 无额外约束 |
| 剧本拆解 | 只拆文本，不生成图 |
| 分镜补全 | 只补镜头，不改已有镜头 |
| 画布整理 | 只调位置与分组 |
| 接片检查 | **只读不写** |

这样做的原因很实际：让模型「自觉不要做某事」不可靠，但把「不许调用写工具」
写成模式约束后，工具调用序列是可检查的。

停止生成走主进程 `ai:abort`，真的中断上游流，不是只把界面按钮改回「发送」。

## 6. 本地服务：谁负责拉起、怎么判断活着

### 三道路障保证「只用本机模型」

1. **预设层**：启动时丢弃所有非回环通道。
2. **存储层**：写入前归一化，云端配置直接拒绝。
3. **请求出口**：主进程对 `baseUrl` 做正则硬校验。

```ts
const LOOPBACK = /^https?:\/\/(127\.0\.0\.1|localhost|\[::1\])(:|$)/i;
```

非回环直接抛错，错误信息里带 host 名 —— 用户能立刻看出是哪条配置在捣鬼。

### 探活：TCP 而不是 HTTP

早期用 `/healthz` 判断服务是否就绪，问题是在下游还没起来时要等 HTTP 超时（4 秒）。
配置检测要连查 5 项，就是 20 秒白等。

改成 `net.Socket` 探端口：

```ts
portOpen(3911) // 毫秒级返回 true/false
```

端口有监听就认为服务在，直接发请求；没有就拉起。
`ensureBackend()` 带 10 秒缓存，避免连续点击重复拉起。

### 模型下载

- 源顺序：ModelScope → HF 镜像 → HF 直连，某个源不通自动换。
- 断点续传：Range 请求 + 本地字节校验。
- 进度：`bytesDone / percent / speed / etaSec` 四项，速度用**窗口增量 EMA**。
  早期用总字节 / 总耗时算平均速度，断点续传时会算出 380MB/s 这种假数字。

## 7. 打包与混淆

```
npm run build        tsc（主进程）+ vite（渲染层）
npm run build:obf    javascript-obfuscator 过一遍两个产物目录
npm run dist:win     electron-builder → NSIS
```

### 两档强度的理由

| 层 | 控制流平坦化 | 原因 |
| --- | --- | --- |
| 渲染层 | 开，阈值 0.3 | 跑在 Chromium 里，出问题立刻在界面上暴露，能当场发现 |
| 主进程 | **关** | 全是长异步链路，平坦化会把 `await` 序列改写成状态机，问题表现为「任务卡住」「下载永远 0%」，且只在某条分支复现 —— 花几小时也未必查得回来 |

字符串加密 + 标识符重命名已经拿走 90% 的收益，剩下 10% 不值得拿主进程稳定性去换。

### 刻意关闭的两个选项

- `selfDefending`：让代码对格式化敏感，用户或客服想排查问题时反而添乱。
- `debugProtection`：`debugger` 死循环会卡死调试器。

### 字符串阈值必须拉满

`stringArrayThreshold: 1.0`。0.65 的时候实测残留 1000+ 段可读中文，
用 `grep` 就能把功能清单翻出来 —— 那等于没混淆。

### 打包完整性

- `asar: true`，代码在 `app.asar` 里
- `extraResources`：图标、`deploy/` 目录
- NSIS：非一键安装、可改目录、建桌面与开始菜单快捷方式
- 刻意不写 `publisherName`，避免与证书 CN 的等值校验失败导致签名报错

## 8. 双宿主同构（开发便利，不是产品形态）

同一套渲染层能在两个宿主里跑：

| 宿主 | 桥接方式 |
| --- | --- |
| 桌面 | `preload.ts` 的 `contextBridge.exposeInMainWorld('yj', ...)` |
| 浏览器 | `web/shim.ts` 把 `window.yj.*` 代理到 `/api/rpc` |

用途是开发期在浏览器里快速调 UI，不用每次都起 Electron。
0.1.0 只发布桌面端 —— 浏览器宿主缺少本地文件、模型下载、ffmpeg 这些能力，
**不构成可用产品**。

## 9. 验证方式

作者的验收口径是「外部可观测」，不看内部状态：

- **类型**：两个 tsc（渲染层 + 主进程）零错误
- **构建**：vite build 零 warning
- **纯逻辑自检**：剧本拆解、分组收录、容器成员
- **真机 E2E**：Playwright 驱动真实 Electron，断言走 DOM 回显、剪贴板内容、
  节点数量、磁盘上是否真有那个文件
- **能力对账**：界面上的比例 / 分辨率选项必须等于 `capabilityOf()` 的推导结果 ——
  这一条能抓住「界面写死枚举」这类回归

生成链路的测试用本地 mock 上游（真实 Electron + 真实落盘），
跑测试会临时替换 providers 配置并在结束后恢复，不会打真实接口。
